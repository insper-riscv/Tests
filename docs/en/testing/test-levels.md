# VHDL test levels

🌐 [Português](../../pt-br/testing/test-levels.md) · [English](test-levels.md)

The RV32IM VHDL goes through nine verification levels, from the cheapest and fastest to the most expensive and closest to the real hardware. Each level catches a class of error the previous ones do not, and none replaces the next.

## 1. Overview

| Level | Name | Checks | Tool | Where it runs |
| :---: | :--- | :--- | :--- | :--- |
| 0 | Static consistency | the manual copies of the memory map and the file paths | `riscv-tools check-memory-map`, `check-paths` | simulation CI and the CI of each repository |
| 1 | Analysis and elaboration | the VHDL compiles and the top elaborates | GHDL | CI of each repository |
| 2 | Entity | the behavior of an isolated block | cocotb + GHDL | CI of each repository |
| 3 | Program on the full core | the pipeline executes real programs | cocotb + GHDL + Spike | simulation CI |
| 4 | Platform with SDRAM | the core with the SDRAM, the controller, and the chip model | cocotb + GHDL | simulation CI |
| 5 | Simulated hardware top | the board top with the Intel models of the memories | GHDL + Quartus libraries | manual, on the runner with Quartus |
| 6 | Synthesis | the VHDL is synthesizable and fits the FPGA with timing | `ghdl --synth`, Quartus | Quartus in the real-hardware CI; `ghdl --synth` manual |
| 7 | Formal | properties valid for all states | SymbiYosys | manual |
| 8 | Board | the result on the FPGA, with real delays | BIST over JTAG, `riscv-tools run` | real suite in the real-hardware CI (self-hosted runner); BIST manual |

Three terms appear throughout the text.

| Term | Meaning |
| :--- | :--- |
| Golden | the expected result of a program, that is, the memory contents at the end of the execution, generated by Spike (the reference simulator) or versioned along with the test |
| `tohost` | the 64-bit memory word where the program writes the verdict when it ends (1 is PASS, `(code << 1) | 1` is FAIL), read by the testbench or over JTAG |
| Tick | the simulation time unit; the base clock has three ticks per core cycle |

## 2. Level 0, static consistency

The memory map (where the boot ROM, the FLASH, the RAM, and the reserved words live) is copied by hand in many places: test configuration, linker flags, boot ROM, runtime, core VHDL constants, memory IPs, and testbench. The `platform.yaml` of each platform is the source of truth, and `check-memory-map` checks each copy against it, for the `internal-mem` platform and for the `sdram` one. `check-paths` checks that every path listed in the manifest exists.

| | |
| :--- | :--- |
| Catches | address or size that differs between two copies, moved or renamed file |
| Does not catch | any hardware behavior |
| Commands | `riscv-tools --root Insper-RISC-V check-memory-map --platform src/<family>/<platform>/platform.yaml` and `make paths` |
| Cost | seconds, no simulator |

## 3. Level 1, analysis and elaboration

GHDL analyzes the VHDL-2008 files in the dependency order that `riscv-tools vhdl-sort` computes and elaborates the simulation top. A syntax, type, or port error shows up here, before any simulation.

| | |
| :--- | :--- |
| Catches | syntax, type, or port error, circular dependency |
| Does not catch | wrong logic that compiles |
| Command | `make check`, in each repository |
| Cost | seconds |

## 4. Level 2, entity

Each VHDL block has a Python (cocotb) testbench that drives the ports directly and checks the outputs, without the compiler or the simulation flow of `riscv-tools`. The tests live in the repository of the block.

| Repository | Tested blocks |
| :--- | :--- |
| Core | register file, ALU, instruction decoder, immediate and RAM extenders, store manager, control unit, M decoding, hazard detection, forwarding, bubble mux, and the pipeline stall with variable-latency memory |
| Memory | simulation RAM and ROM, the SDRAM system (controller, bridge, and chip model), the self-test (BIST) with and without registers on the pins, the JTAG debug port, and the external bus (interconnect and JTAG UART) |
| Peripherals | GPIO, TIMER, the operation decoders, MUX4, MUX8, and the tri-state buffer |
| Insper-RISC-V | the clock generator of the top |

The SDRAM tests run against a chip model that **aborts the simulation** on any violation of timing (tRCD, tRP, tRAS, tRC, tRFC, tWR, tMRD), command order, power-up sequence, mode register, burst overlap, or refresh interval. A defect injected on purpose into the controller (short tRCD, no refresh, ACTIVE too early, read capture too early, 24-bit fill counter) must make some test fail; this confirms that the tests do not pass vacuously.

| | |
| :--- | :--- |
| Catches | logic error in a block, handshake protocol, corner case of a state machine |
| Does not catch | integration error between blocks, or an error that only appears when running a program |
| Commands | `make test` (all) or `make test TEST=<name>`, in each repository |
| Cost | minutes per repository |

## 5. Level 3, program on the full core

The simulation top gathers the core, the boot ROM, and the FLASH, and runs the suite of assembly and C programs. The flow of each program has two steps.

1. `riscv-tools compile --emit hex` compiles the program with the RISC-V GCC (picolibc) and generates the memory images.
2. `riscv-tools sim` loads the image, runs the core until the program writes the verdict to `tohost`, and compares the result with the golden.

| Program type | Golden |
| :--- | :--- |
| Assembly | versioned along with the test |
| C with memory check | generated by Spike |
| C that only signals PASS or FAIL | none; the `tohost` verdict counts |

The time of each program, in ticks, is also recorded and serves as the basis to measure the cost of a memory change.

| | |
| :--- | :--- |
| Catches | wrong instruction, hazard, or forwarding that only appears in sequence, integration between pipeline, memories, and boot |
| Does not catch | SDRAM behavior, pin timing, synthesizability |
| Commands | `riscv-tools --config tools/riscv_build/config.yaml generate-header`, `compile --emit hex`, and `sim` |
| Cost | minutes for the whole suite |

## 6. Level 4, platform with SDRAM

The `sdram` platform uses the 64 MB SDRAM as the only RAM of the core, through the bridge, the arbiter, and the controller, with the chip model of level 2. There are two suites.

| Suite | Configuration | What runs | Verdict |
| :--- | :--- | :--- | :--- |
| Regression | `config.sdram-flash-regression.yaml` | the same programs as level 3 | the result must be identical to that of `internal-mem` |
| SDRAM programs | `config.sdram-flash.yaml` | programs that use the SDRAM on purpose (byte access, copy, loop, memory test, multiplication and division with operands in the SDRAM, refresh) | each program checks itself and signals PASS or FAIL |

At the end of a passing program, the testbench compares the golden with the **contents of the chip model**, not with the writes seen on the bus. A word that never reached the chip, or reached the wrong address, is caught.

The ratio between the SDRAM cycles and the internal RAM cycles, measured on the same programs, sizes a data L1 cache.

| | |
| :--- | :--- |
| Catches | SDRAM protocol error in the whole system, data that does not reach the chip, core regression when the memory is swapped |
| Does not catch | pin delay, clock phase, and real timing, which the simulator does not model |
| Commands | those of level 3 with the two configurations above |
| Cost | minutes per suite |

## 7. Level 5, simulated hardware top

The top that goes to the board instantiates memories generated by Quartus. This level simulates that top with the memories as Intel models (the `altera_mf` library, shipped with Quartus) and runs the suite on it. No board is touched.

| | |
| :--- | :--- |
| Catches | behavior difference between the simulation memory model of levels 3 and 4 and the real memory IP |
| Does not catch | synthesis and timing |
| How it runs | manual workflow, on the self-hosted runner that has Quartus, inside the toolchain image with Quartus mounted read-only |
| Cost | time of a full simulation |

## 8. Level 6, synthesis

Two independent checkers answer different questions.

| Checker | Question |
| :--- | :--- |
| `ghdl --synth` | does the VHDL describe synthesizable hardware? A file with `wait for 10 ns`, for example, is rejected |
| Quartus (analysis and synthesis, fitter, timing) | does the design fit the FPGA and does the timing close? |

`ghdl --synth` is more permissive than the VHDL-2008 subset that Quartus accepts, so passing it does not guarantee that Quartus accepts the code. It serves as a fast, license-free check, and as the first step of the formal verification of level 7.

The Quartus timing is checked on the slow model at 85 °C, with the chip times from the SDRAM datasheet (ISSI IS42/45S16320D, grade -7). A negative margin on any path fails the design. The paths checked on the `sdram` platform are the following.

| Path | Domain |
| :--- | :--- |
| SDRAM data read | controller |
| commands and write data | SDRAM clock pin |
| core logic | core clock |

| | |
| :--- | :--- |
| Catches | construct that simulates and does not synthesize, Quartus subset, resources and timing |
| Does not catch | functional behavior |
| Commands | `ghdl --synth --std=08 --out=verilog <entity>` and `quartus_sh --flow compile <project>` |
| Cost | seconds for `ghdl --synth`; a few minutes for Quartus |

## 9. Level 7, formal verification

SymbiYosys proves properties for **all** possible states, not only for those that a testbench exercises. The VHDL is converted to Verilog by `ghdl --synth`, and the properties live in SystemVerilog around the netlist. The environment is described by assumptions: a master only changes the toggle after seeing the response and holds the buses until then, and the controller responds within 4 clocks.

The verified block is the arbiter that shares the SDRAM controller between the core and the debug port.

| Property | Kind of proof |
| :--- | :--- |
| there are never two requests to the controller at the same time, and the buses stay stable while it is pending | induction, with no depth limit |
| each grant carries the word of a master that was waiting | induction |
| each request gets a single response, with the right toggle, and the data read is the one returned by the controller | induction |
| a request is answered within 14 clocks at most, with the controller answering within 4 | verification up to depth 45; 13 clocks are not enough |

A defect injected into the arbiter (read data swapped between the masters, or a response without waiting for the controller) is caught by the properties. Two changes to the priority rule between the masters are not caught, because the toggle protocol already prevents starvation: a master only repeats the request after seeing the response, and in that interval the arbiter serves the other.

| | |
| :--- | :--- |
| Catches | protocol violation in some rare state that no simulated test reaches |
| Does not catch | everything outside the model, that is, a single reset at the start, a controller with bounded response, and clocks treated as one |
| Command | `sby -f <file>.sby` |
| Cost | seconds per proof in this block |

## 10. Level 8, board

Two tests on the FPGA, with real pin delays, clock phase, and timing.

| Test | Programmed design | What runs |
| :--- | :--- | :--- |
| SDRAM self-test (BIST) | `sdram-bringup`, without the core | four modes over JTAG: fast with byte masks, patterns, sweep of the whole chip, and random addresses; the criterion is zero wrong words |
| Real suite | `core_fpga_sdram`, with the core | `riscv-tools run`: loads each program through the JTAG debug port and reads the result back, checking the goldens |

The real suite measures correctness, not cycles. The time of each program is dominated by loading and reading over JTAG, and the cost in cycles comes from level 4.

| | |
| :--- | :--- |
| Catches | what only the hardware shows, such as pin delay, clock phase, read capture, and the JTAG chain |
| Does not catch | variation between boards, temperatures, and lots, which requires repeating under other conditions |
| Commands | `quartus_stp -t jtag/sdram_bist.tcl <mode>` and `riscv-tools --config <config> run` |
| Cost | minutes per run, plus the Quartus compilation |

## 11. Which level catches which error

| Error class | First level that catches it |
| :--- | :--- |
| memory map address different in two copies | 0 |
| syntax, type, or port error | 1 |
| wrong logic in a block | 2 |
| wrong instruction or hazard in a program sequence | 3 |
| SDRAM protocol violated, data that does not reach the chip | 4 |
| real memory IP that behaves differently from the model | 5 |
| VHDL that simulates and does not synthesize | 6 |
| protocol violation in a state that no test reaches | 7 |
| pin delay and clock phase | 8 |

The SDRAM read capture is a class of level 8. The simulation model with registers on the pins assumes one more cycle between the pin and the register than the hardware has, and no level from 0 to 7 shows the difference; only the self-test on the board reports the wrongly read words.
