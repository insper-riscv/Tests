# RISC-V test pipeline

Compiles bare-metal test programs (C under `c/` and `c-sdram/`, assembly under
`asm/`, `asm-sdram/` and `asm-hpm-reduced/`) and runs them two ways, and reports PASS/FAIL:

- **real**: every test, on an actual FPGA over JTAG.
- **sim**: every test, in a GHDL/cocotb simulation, no hardware
  needed; a `memory`-kind test's RAM is reconstructed from the bus
  writes the simulation observes and compared against `golden.json`,
  the same check the real suite does from a JTAG dump.

Both are driven by [`riscv-tools`](https://github.com/insper-riscv/Tools), which the
`ci-*` and `dev_tools` images of [Infra](https://github.com/insper-riscv/Infra) carry; this
repository holds no copy of it. This folder only holds what is specific to the tests: the
`config*.yaml` files, which extend the platform configuration that `riscv-tools platform sync`
generates from the [Insper-RISC-V](https://github.com/insper-riscv/Insper-RISC-V) submodule
(toolchain, memory map, runtime, Quartus project and simulation top), and `uart_hardware_test.py`,
the host harness of the physical UART. Everything else (compiling, JTAG programming and readback,
RAM-versus-golden comparison, running the simulation) is `riscv-tools` code, fixed and extended
in one place instead of drifting between copies.

## Configurations

| File | Platform and programs |
| :--- | :--- |
| `config.yaml` | `internal-mem` platform (ROM and RAM inside the FPGA, `core_fpga_test` top): the programs of `asm/` and `c/` |
| `config.fpga-sim.yaml` | The same platform simulated with the Quartus memory models (`sim-fpga.yml`) |
| `config.sdram-flash-regression.yaml` | `de0-cv` platform (BOOT_ROM in the core, FLASH and SDRAM behind the caches): the programs of `asm/` and `c/`, with the same results as `internal-mem` |
| `config.sdram-flash.yaml` | `de0-cv` platform: the programs of `asm-sdram/` and `c-sdram/`, which use the SDRAM and the FLASH |
| `config.sdram-flash-lat*.yaml`, `config.sdram-flash-regression-lat*.yaml`, `config.sdram-flash-slow.yaml` | The two above with other FLASH latencies, for the simulation |
| `config.hpm-reduced.yaml`, `config.hpm-reduced-asm.yaml` | `internal-mem` simulation with 4 event counters of 40 bits, for `asm-hpm-reduced/` |
| `config.platform-*.yaml` | Generated by `riscv-tools platform sync`; never edited by hand |

## Writing a test

Create a folder named for what the test does, under `c/` (for a `.c`
source) or `asm/` (for a `.S` source), containing a `src.c`/`src.S`:

```
c/
└── my-test/
    └── src.c
```

Two optional header comments configure it:

```c
// RV32_EXT: M          // extensions ADDED to the implicit rv32i base.
// RV32_EXT: M,A        // order doesn't matter: both this and "A,M" become rv32ima.
// RV32_TEST_KIND: unit          // default. Checked via `tohost` (PASS or FAIL)
                                  // alone. Builds for both real hardware and sim.
// RV32_TEST_KIND: memory        // tohost + a full RAM dump compared against
                                  // c/my-test/golden.json. Verified on both
                                  // real hardware (JTAG dump) and sim (bus-
                                  // snooped writes).
#include "rv32_test.h"

int main(void) {
    // ... RV32_PASS() or RV32_FAIL() when done ...
}
```

`rv32_test.h` is **generated**, not checked in (see `.gitignore`);
`riscv-tools generate-header` writes it from `config.yaml`'s
`memory.tohost_addr` (see "Running locally" below). Regenerate it
after changing that address; don't hand-edit the generated file.

A `memory` test needs a matching `golden.json` next to its
`src.c`/`src.S`: byte address (hex string) -> expected value (0-255).
`riscv-tools compile` fails fast if it's missing. See
[`docs/pt-br/creating-a-c-test.md`](https://github.com/insper-riscv/Tools/blob/main/docs/pt-br/creating-a-c-test.md)
in the Tools repository for the full reference.

## Running locally

Everything runs in the `dev_tools` image of Infra, which carries the RISC-V GCC with picolibc, Spike,
GHDL, `uv` and `riscv-tools`; only the board steps need Quartus on the host. From the root of this
repository, with the submodules initialized (`git submodule update --init --recursive`):

```bash
docker run --rm -v "$PWD:/w" -w /w ghcr.io/insper-riscv/dev_tools:latest bash -c '
  uv sync
  riscv-tools --config tools/riscv_build/config.yaml generate-header   # once, or after changing tohost_addr
  riscv-tools --config tools/riscv_build/config.yaml compile --emit hex
  riscv-tools --config tools/riscv_build/config.yaml sim'
```

On the host, with Quartus and a board on JTAG (the compile step stays in the image):

```bash
riscv-tools --config tools/riscv_build/config.sdram-flash-regression.yaml generate-header
riscv-tools --config tools/riscv_build/config.sdram-flash-regression.yaml compile --emit mif
riscv-tools --config tools/riscv_build/config.sdram-flash-regression.yaml run \
  --exclude uart-echo,uart-tx,uart-errors --skip-reconfigure   # the board already holds the bitstream
```

`compile` iterates every `<name>/src.c`/`<name>/src.S` folder under the program folders of the
configuration and writes `build*/{real,sim}/manifest.json`; both `--emit mif` and `--emit hex` build
every test regardless of kind and attach a `memory`-kind test's `golden.json` to its manifest entry,
which `run`/`sim` then consume. The per-entity VHDL unit tests are documented in
[tests/python/README.md](../../tests/python/README.md).

The board run starts from whatever the SDRAM holds, because the host zeroes only the words of the
`tohost`/`fromhost` protocol between programs. A program that reads a RAM word before writing it must
clear that word first.

## Integrated UART hardware check

The normal JTAG/tohost-only `riscv-tools run` flow cannot validate the UART
tests by itself: `uart-echo` and `uart-errors` need external serial traffic,
while `uart-tx` can report tohost PASS without proving that the expected bytes
reached the physical pin. After compiling Quartus with
`build/real/uart-echo.mif`, close `picocom`, connect the Pico/Debug Probe UART,
and run:

```bash
uv run python tools/riscv_build/uart_hardware_test.py --port /dev/ttyACM0
```

By default the harness validates all three programs. As a consistency guard, it
checks that `quartus/init.mif` is byte-for-byte identical to the compiled
`uart-echo.mif` and that the `.sof` is newer. It then:

1. opens the serial port in raw 115200 8N1 and reprograms the existing `.sof`;
2. sends `RX test\r\n`, requires the exact nine-byte echo and `TOHOST=1`;
3. replaces both FLASH copies with `uart-tx.mif` over JTAG, restarts through
   the boot ROM, and requires the exact `Hello, world!\r\n` output plus
   `TOHOST=1`;
4. loads `uart-errors.mif`, fills the TX path with the 17 accepted bytes `A`
   through `Q` (one in the physical transmitter and 16 in the FIFO), rejects
   an extra `X`, and requires the exact accepted stream followed by the `R`
   prompt; the firmware checks `TX_LEVEL`, `TX_DROPPED` and its W1C clearing;
5. sends 17 bytes (`00` through `10`) without allowing the firmware to consume
   RX, then requires `O`; the firmware proves that the 16-byte RX FIFO kept
   `00` through `0f` in order, discarded only `10`, reported `RX_OVERRUN`, and
   cleared it through W1C;
6. sends one raw 32-byte burst (`00` through `1f`), requires the exact echo plus
   the final `P` marker, no new error flags, and `TOHOST=1`.

Running the baked-in echo first is intentional: it leaves the CPU parked in
the boot ROM, where replacing FLASH for the later tests is safe. Reprogramming
first makes the whole sequence repeatable on every invocation. Individual
selection is available for diagnostics:

```bash
uv run python tools/riscv_build/uart_hardware_test.py --test uart-echo
uv run python tools/riscv_build/uart_hardware_test.py --test uart-tx
uv run python tools/riscv_build/uart_hardware_test.py --test uart-errors
```

Every selection still performs the echo bootstrap before replacing FLASH;
`all` is the default and reports all three checks explicitly.

To exercise arbitrary echo data while keeping the firmware's fixed length:

```bash
uv run python tools/riscv_build/uart_hardware_test.py \
  --payload-hex "00 55 aa 0d 0a 7f 80 fe ff"
```

`--skip-program` exists only for debugging immediately after a manual FPGA
programming, before any byte has reached `uart-echo`; it is not suitable after
the firmware has already written PASS. The real-hardware workflow uses it only
because its immediately preceding step has just compiled and programmed the
`uart-echo` baseline.

The serial framing, exact-byte validation, timeout handling, artifact guards,
and JTAG restart ordering have host-only tests that need no board:

```bash
uv run python -m unittest discover -s tests/host -v
```

## CI

Each suite has its own workflow file:

- [`.github/workflows/sim.yml`](../../.github/workflows/sim.yml):
  runs on any push/PR/branch, on a standard GitHub-hosted runner
  (inside the `ci-elf` image, no license needed). Also
  triggerable manually via **Actions → sim tests → Run workflow**. Its generic
  top instantiates the UART, so `uart-tx`, `uart-echo` and `uart-errors` run in
  the normal suite beside the other programs. Cocotb decodes the serial 8N1 output,
  requires exactly `Hello, world!\r\n` from `uart-tx`, injects `RX test\r\n`
  into `uart-echo` and requires the same bytes back, then validates the error
  flags, W1C behavior and 32-byte burst protocol with `uart-errors`. The
  workflow also runs the host-side unit tests for the physical UART harness.
- [`.github/workflows/real.yml`](../../.github/workflows/real.yml):
  only on `main`, or on demand via **Actions → real tests (FPGA) → Run
  workflow**. Needs a self-hosted runner with Quartus and a board
  attached. It compiles one `uart-echo` baseline, runs all three physical UART
  tests through the dedicated harness, then runs the remaining tohost-only
  suite without another Quartus compile.
- [`.github/workflows/sim-fpga.yml`](../../.github/workflows/sim-fpga.yml):
  runs the complete manifest, including all three UART programs, against the real
  hardware top and Quartus memory models on the self-hosted runner.

The manual `real` and `sim-fpga` forms test the version of Insper-RISC-V (and of the
repositories inside it) that this repository pins as a submodule.

Both check out the submodules recursively and set up `uv` the same way local dev does above. The
ACT4 certification lives in [`insper-riscv/Certification`](https://github.com/insper-riscv/Certification).

## Real-hardware runner

`real.yml` and `sim-fpga.yml` run on a self-hosted runner labelled `quartus` (and `fpga` for the one
with the board). The runner provides Quartus (mounted read-only from `/opt/altera_lite`), the board on
JTAG and Docker; everything else runs in the `ci-elf` image. The generic setup (service account,
registration, systemd unit, the manual-dispatch secret and the USB-autosuspend gotcha of the JTAG
cable) is in [RUNNER_SETUP.md](https://github.com/insper-riscv/Infra/blob/main/docs/pt-br/RUNNER_SETUP.md)
of Infra. What is specific to the tests:

- the JTAG device is `@1: 5CE(BA4|FA4) (0x02B050DD)`, and the cable name changes with the USB port, so
  scripts find it by the IDCODE `02B050DD` in the `jtagconfig` output;
- the Quartus project of the `de0-cv` platform is in `Insper-RISC-V/src/cyclone-v/de0-cv`, with the
  In-System Memory Content Editor instances for the FLASH and the SDRAM debug port that the
  `htif`, `ram_dump`, `rom_writer` and `sdram_debug` modules of `riscv-tools` rely on;
- the memory map (BOOT_ROM, FLASH, SDRAM, and the `tohost` and `fromhost` words) is the
  `platform.yaml` of the platform, and `riscv-tools check-memory-map` checks every copy of it.
